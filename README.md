# Ledger — Bank Statement Analyzer

Upload a bank statement PDF, get a readable dashboard: income vs expenses,
balance over time, largest transactions, and a short plain-language summary
generated by a local LLM. Everything runs on your machine — no data leaves it.

## What this project does

1. **Parses** a bank statement PDF using x/y text positioning (`parse.py`) —
   handles varying column layouts by auto-detecting header positions, and
   validates every row against the statement's own running balance.
2. **Analyzes** the parsed transactions (`analyze_statement.py`) — computes
   totals, monthly breakdowns, and shapes chart-ready JSON.
3. **Serves** a single-page dashboard (`app.py` + `templates/` + `static/`) —
   upload a PDF, get back an interactive Chart.js dashboard and an LLM-written
   summary, no page reloads.

## Local LLM (for insights, categorization, and chat)

The dashboard's narrative summary, spending categories, and chat all run
through [Ollama](https://ollama.com) — no data or API calls leave your
machine.

```bash
ollama pull qwen2.5:7b          # chat + insights + categorization
ollama pull nomic-embed-text    # embeddings for the RAG retriever
```

Ollama runs as a background service once installed. If it isn't running, or
the RAG stack (`langchain`/`chromadb`) isn't installed, the app still works —
it falls back to a simpler prompt-based chat and skips the category chart,
rather than failing. See **AI Engineering Highlights** below for details.

To use a different model:
```bash
# Windows (PowerShell)
$env:OLLAMA_MODEL = "qwen2.5:14b"
# macOS/Linux
export OLLAMA_MODEL="qwen2.5:14b"
```

To disable the RAG stack entirely (always use the simpler chat path):
```bash
$env:USE_RAG = "0"     # PowerShell
export USE_RAG=0       # macOS/Linux
```

## Run it

```bash
python app.py
```

Open **http://127.0.0.1:5000**, upload a statement PDF, and click **Analyze
statement**.

## AI Engineering Highlights

This project went through a deliberate progression — plain prompting first,
then real retrieval — which mirrors how these systems actually get built:

**Retrieval-Augmented Generation (`rag_chat.py`)**
Every transaction is embedded (`nomic-embed-text` via Ollama) and stored in
an in-memory Chroma vector store, rebuilt fresh per uploaded statement. Chat
questions retrieve only the semantically relevant transactions — asking
"how much did I spend on food?" retrieves grocery/restaurant transactions
by meaning, not by keyword match, even if the word "food" never appears in
any narration.

**LangChain (LCEL)**
The chat and categorization paths are composed as LangChain Expression
Language chains — `retriever | prompt | model | structured_output` — rather
than hand-rolled string concatenation and raw API calls. This is the modern
LangChain pattern (as opposed to the older, now-discouraged `LLMChain`
class-based API).

**Structured output over free text**
Both the chat answer and the transaction categorizer return Pydantic-
validated objects (`ChatAnswer`, `CategorizationBatch`), not raw strings
parsed with regex. Also worth noting: the chat's "is this on-topic?"
decision is a structured boolean field the model sets, not a magic string
match — and the "sources" shown to the user come directly from the
retriever's metadata, not from asking the model to self-report which
transactions it used (which risks hallucinated citations).

**LLM-based categorization**
`categorize_transactions()` batches transactions (default 40 per call) into
one structured-output request per batch rather than one call per
transaction — a basic but real efficiency consideration once you're paying
per-call latency.

**Evaluation (`eval_rag.py`)**
A small harness computing Recall@k and Precision@k for the retriever against
a labeled set of (question, expected transaction) pairs you define for your
own statement. The scoring logic has its own test:
```bash
python eval_rag.py --test-scoring
```

**Graceful degradation as a design principle, not an afterthought**
Every LLM-dependent feature (insights, categorization, RAG chat) is wrapped
so its absence degrades the experience rather than crashing it: no Ollama
running → charts and the table still work; RAG stack not installed → chat
falls back to the simpler prompt-based version; categorization fails → that
chart card just doesn't render. This mirrors production practice: an AI
feature should never take down the parts of an app that don't need it.

## Project structure

```
app.py                  Flask app: page route + two JSON API routes (analyze, chat)
parse.py                PDF -> structured transactions (the parsing engine)
analyze_statement.py    Transactions -> summary stats, chart data, simple LLM chat/insights
rag_chat.py             RAG + LangChain: embeddings, retrieval, structured-output chat/categorization
eval_rag.py             Retrieval evaluation harness (Recall@k / Precision@k)
templates/index.html    Single-page shell
static/styles.css       Design system
static/app.js           Upload handling, Chart.js rendering, chat, table rendering
requirements.txt
```

## Using `parse.py` / `analyze_statement.py` outside the web app

Both modules are plain Python and work standalone — useful if you want to
batch-process statements or explore the data in a notebook:

```python
import pandas as pd
from parse import parse_bank_statement
from analyze_statement import print_insights, generate_charts, generate_llm_insights

result = parse_bank_statement("statement.pdf")
df = pd.DataFrame(result["transactions"])
df["date"] = pd.to_datetime(df["date"], dayfirst=True, errors="coerce")
for col in ["withdrawal", "deposit", "balance"]:
    df[col] = pd.to_numeric(df[col].replace("", None), errors="coerce")

print_insights(df)              # text summary in the terminal
generate_charts(df)             # saves PNG charts to ./charts/
print(generate_llm_insights(df))
```

## Troubleshooting extraction issues

If transactions come out missing, misaligned, or with truncated descriptions
on a new bank's statement layout, run the parser directly with `--debug` to
see exactly how text is being read off the page:

```bash
python parse.py your_statement.pdf --debug --verbose
```

This prints every detected text block's position — the same view used to
diagnose and fix column-detection and description-truncation issues during
development.

## What's deliberately *not* here

Earlier prototyping explored a generic CSV/XLSX/JSON ingestion path and a
19-field finance schema mapped via `llama-cpp-python`. Neither was reliable
or necessary for the actual product (bank statement PDFs), so both were
removed in favor of the focused pipeline above.
